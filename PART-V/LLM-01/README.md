# LLM-01 · 근거 기반 자연어 설명 생성

## 목적
MODEL-01 v3.1이 산출한 브랜드-상권 적합도 결과(순위, 점수, 구조화된 근거)를
사람이 읽을 수 있는 자연어 설명으로 변환한다.
새로운 근거를 생성하지 않고, 모델이 이미 허용한 사실(`llm_allowed_facts`)만
문장으로 옮기는 것이 원칙이다.

## 사용한 입력 파일
- `PART-III/MODEL-01/outputs/final_model_v3_1/model01_final_recommendations_v3_1.parquet`
  브랜드×상권 조합별 행. `final_rank`, `final_suitability_score`,
  `positive_drivers`, `caution_flags`가 핵심 컬럼.
- `model01_brand_availability_v3_1.csv`
  브랜드별 후보 풀 크기, 추천 가능 개수(`available_recommendation_count`, 최대 20).

**주의**: MODEL-01 v3의 `structured_evidence` 필드는 사용하지 않는다
(README상 LLM/앱 사용 금지 필드).

## 대상 범위
- 전체 24개 브랜드 (제과·베이커리 프랜차이즈로 한정된 브랜드 풀).
  이 범위가 최종 확정치인지, 데이터 품질 문제로 일부 브랜드가 제외된 것인지는
  DATA-01의 `data01_quality_report_addendum.md` 참고 필요.
- 브랜드별 상위 3개 상권만 자연어 설명 생성 (4위 이하는 아래 "향후 제안" 참고).

## 처리 로직

### 1. 순위 재계산 (동점 처리)
- `final_suitability_score`(0~1 스케일) 기준 내림차순 정렬.
- 인접한 두 값의 차이가 **0.003 이하**면 동일 순위로 처리 (1,1,2 방식).
  100점 만점 기준으로는 0.3점 이내 차이.
- 이 임계값은 24개 브랜드의 1~3위 점수 차이 분포(1~2위 평균 gap 0.034,
  2~3위 평균 gap 0.016)를 참고해 정한 값으로, 엄밀한 통계적 도출이 아니라
  실측 분포 기반의 어림값이다. 브랜드 풀이 바뀌면 재검토 필요.
- **"상위 3위까지"가 아니라 "상위 3개 상권까지"**가 원칙이다.
  동점 그룹이 3개보다 많아도, 점수 순서대로 상위 3개만 남기고 나머지는 버린다.

### 2. 백분위 표시
- 원본 percentile(예: `absolute_fit_percentile`)은 "값이 높을수록 좋다"는 의미이므로,
  `(1 - percentile) * 100`으로 뒤집어 "상위 X%"로 표시한다.
- 계산값이 0.01보다 작으면 0.01로 올려서 표시한다 ("상위 0.00%" 방지).
- 표시 소수점은 둘째 자리까지. (일부 값이 "xx.x0%"처럼 보이는 경우가 있는데,
  이는 표시 로직 문제가 아니라 원본 percentile 계산 자체의 특성으로 보인다.
  일부 상권이 완전히 동일한 percentile 값을 공유하는 경우가 확인됨 —
  정확한 계산 방식은 모델 담당자에게 확인 필요.)

### 3. 코드 → 자연어 매핑
`code_to_text_mapping.json`에 두 종류의 매핑이 있다.

**positive_drivers (4개, 전체 스캔으로 확정된 목록)**
| 코드 | 한글 표현 |
|---|---|
| `brand_environment_fit` | 소비환경과의 적합도 |
| `brand_specific_advantage` | 다른 브랜드 대비 상대적 강점 |
| `market_opportunity` | 제과 시장 규모 (※ "시장 기회"라고 쓰지 않음) |
| `low_competition_risk` | 경쟁 우위 |

**caution_flags (5개, 전체 스캔으로 확정된 목록)**
| 코드 | 처리 |
|---|---|
| `competition_risk_elevated_but_below_exclusion` | 경쟁 문단에 포함, "출점 전 참고" 문구 없음 |
| `competition_risk_moderate` | 경쟁 문단에 포함, "출점 전 참고" 문구 없음 |
| `no_model_level_caution_flag` | null 처리 (문장에서 제외) |
| `profile_stability_moderate` | 별도 주의 문단에 포함, "출점 전 참고가 필요합니다"로 마무리 |
| `same_brand_distance_750m_to_1000m_review` | 별도 주의 문단에 포함, "출점 전 참고가 필요합니다"로 마무리 |

- 경쟁 관련 두 코드는 positive_facts의 `low_competition_risk`와 같은 문단에서 다뤄지고,
  나머지 두 코드는 별도 문단("다만, ~. 출점 전 참고가 필요합니다.")으로 처리된다.
  이 틀 문구는 매핑표가 아니라 생성 코드에 고정되어 있다.

### 4. 상권명, 순위 표기
- `area_name`은 원본 데이터 표기를 그대로 사용한다 (예: "방화역 1번").
  임의로 "방화역 1번 출구" 등으로 늘려 쓰지 않는다.
- 조사(이/가, 과/와)는 한글 유니코드 받침 여부로 자동 판별한다.
- 각 상권 문단은 반드시 "[상권명]은 [순위]위이며, 최종 적합도 [점수]점입니다"로 시작한다.

## 생성 방식: 규칙 기반 → LLM(OpenAI API) 다듬기

### 1단계: 규칙 기반 파이프라인 (`generate_explanations.py`)
파이썬 템플릿 문자열로 문장을 조립하는 결정론적 로직.
동일 입력에 항상 동일 출력을 보장하며, 지어내기 위험이 구조적으로 없다.

### 2단계: OpenAI API(gpt-4o-mini) 기반 생성 (`generate_with_llm.py`)
1단계에서 만든 "재료"(순위, 점수, positive_facts, caution_facts)를 JSON으로 정리해
LLM에게 넘기고, 시스템 프롬프트로 아래를 엄격히 제한한다.

- 제공된 JSON 사실 외의 숫자·예상 매출·생존확률·인과관계·매장규모 추천 금지
- positive_facts의 `top_percent`에 "높다/낮다/양호" 등 자체 등급 평가어 금지
  (숫자가 낮을수록 좋다는 판단은 이미 순위로 표현되어 있으므로, 숫자를 보고
  다시 좋다/나쁘다를 매기면 사실을 오염시키거나 왜곡할 위험이 있음 — 실제로
  0.7%라는 낮은(=좋은) 숫자를 "다소 낮다"고 잘못 평가한 사례가 있었음)
- factor 영어 코드명을 한글 명칭으로 정확히 치환 (특히 `market_opportunity`를
  "시장 기회"로 잘못 번역하는 문제가 있어 "제과 시장 규모"로 명시)
- 각 상권 문단에 순위와 "최종 적합도"라는 표현을 반드시 포함
- caution_facts가 없으면 "특별히 확인된 주의 요인은 없습니다"로 서술 (사실 서술이므로 허용)

**LLM에게 맡기지 않은 것**: "왜 이 숫자가 나왔는지"에 대한 해석·이유 설명.
이건 XAI-01이 분석한 변수 기여도 없이 LLM이 추측하면 근거 없는 해석이 될
위험이 크므로, 숫자를 담백하게 전달하는 역할까지만 맡긴다.

### 일관성 검증
동일 입력으로 API를 두 번 호출해 비교한 결과, 24개 중 20개가 조사·접속어
수준의 미세한 표현 차이만 있었고 사실 관계(숫자, 순위, 서술 내용)는 완전히
동일했다. temperature=0.3 설정으로 충분히 안정적이라고 판단.

### 결과가 어색한 경우 (규칙 기반 vs API 비교)
API 버전이 항상 더 자연스러운 것은 아니었다. 일부 경우 규칙 기반 버전이
접속어 사용이나 문장 톤 면에서 더 일관되고 자연스러웠음. 두 방식 모두
결과물로 보관하여 비교 가능하게 함.

## 산출물
- `llm01_final_explanations.json`: 최종 결과. 브랜드별로 `facts`(입력 재료,
  검증/디버깅용)와 `explanation`(최종 자연어 설명, APP-03에서 사용할 텍스트) 포함.
- `code_to_text_mapping.json`: 코드→자연어 매핑표.

## APP-03(대시보드)에 전달할 사항
1. `explanation` 필드의 텍스트를 그대로 화면에 표시하면 됨. `\n\n`은 문단 구분.
2. 순위·점수·상권명 등 구조화된 데이터는 `facts` 필드에서 직접 가져다 써도 됨
   (예: 카드 헤더 디자인, 배지 등 UI 요소는 텍스트에 의존하지 않고 원본 데이터로 그리는 것을 권장).
3. **지표 용어 설명**(아래 섹션)을 대시보드 툴팁이나 도움말로 한 번만 고정 배치할 것을 제안.
4. **제안**: 현재는 브랜드별 상위 3개 상권만 자연어 설명을 제공한다. 사용자가
   4위 이하 상권 정보도 필요로 하는 경우를 위해, "더보기" 버튼 등으로
   `available_recommendation_count`(최대 20, 브랜드별로 다름)까지 전체 순위를
   펼쳐 보여주는 기능을 추가하면 좋을 것 같다. 다만 4위 이하는 현재 자연어
   설명이 없으므로, 구조화된 데이터(순위, 점수, positive_drivers/caution_flags
   원본)만 우선 제공하고 필요 시 자연어 설명 범위를 확장하는 것을 검토할 수 있다.

## 지표 용어 설명 (사용자 노출용)

**1. 소비환경과의 적합도 (brand_environment_fit)**
이 브랜드가 지금까지 입점해온 지역들의 소비 특성(연령대, 소비 패턴 등)과
이 상권의 소비 특성이 얼마나 비슷한지를 나타냅니다. "상위 X% 수준"이라는
표현은 전체 후보 상권들 중 이 상권이 상위 X% 안에 든다는 뜻이며, 숫자가
작을수록 더 적합하다는 의미입니다.

**2. 다른 브랜드 대비 상대적 강점 (brand_specific_advantage)**
같은 상권을 두고 다른 브랜드들과 비교했을 때, 이 브랜드만이 갖는 상대적인
우위를 나타냅니다. 단순히 상권 자체가 좋은 것이 아니라, "이 브랜드이기
때문에" 특히 잘 맞는 정도를 의미합니다. 숫자가 작을수록 우위가 크다는 뜻입니다.

**3. 제과 시장 규모 (market_opportunity)**
해당 상권의 제과·베이커리 업종 전체 매출 규모를 기준으로 산정된 지표입니다.
시장이 크다는 것이 곧 이 브랜드의 성공을 보장하지는 않으며, 단순히 상권의
전체 시장 크기를 나타냅니다.

**4. 경쟁 우위 (low_competition_risk)**
상권 내 경쟁 제과점의 수와 밀집도를 기반으로, 경쟁이 상대적으로 적어 유리한
정도를 나타냅니다. 숫자가 작을수록 경쟁이 적어 더 유리한 상황입니다.

**5. 최종 적합도 점수 (final_suitability_score)**
위 네 가지 요인(소비환경 적합도, 브랜드 상대적 강점, 시장 규모, 경쟁 우위)과
상권 데이터의 안정성 등을 종합적으로 고려하여 산출된 최종 점수입니다. 100점
만점으로 환산하여 표시하며, 이 점수는 예상 매출, 생존 확률, 투자수익률을
의미하지 않습니다. 브랜드의 기존 운영 환경과 상권 특성 간의 적합도를 나타내는
의사결정 참고 지표입니다.

**6. 주의 요인 (caution_facts)**
추천 상권에 출점을 검토할 때 추가로 확인이 필요한 사항입니다. 경쟁 강도가
다소 높거나, 상권 데이터의 안정성이 보통 수준이거나, 인근에 동일 브랜드의
기존 점포가 있어 상권 잠식 가능성이 있는 경우 등이 포함됩니다. 주의 요인이
있다고 해서 추천에서 제외된 것은 아니며, 출점 전 참고할 사항으로 이해하면
됩니다.

**7. 동률(공동 순위) 처리 기준**
여러 상권이 최종 적합도 점수 기준으로 매우 근소한 차이(0.3점 이내, 100점
만점 기준)를 보이는 경우, 순위를 나누지 않고 동일한 순위로 표시합니다. 이는
통계적으로 의미 있는 차이가 아닌 미세한 점수 차이로 순위가 임의로 갈리는
것을 방지하기 위한 기준입니다.

## 확인이 더 필요한 부분 (다른 팀원 협업 필요)
- 복수 출점 조합(2~3개 상권을 함께 검토, 거리·분산·경쟁 차이를 근거로 제시)
  관련 산출물이 별도로 있는지 A에게 확인 필요. 워크플로우 문서상 원래 범위였으나
  현재 받은 parquet에는 개별 상권 단위 데이터만 존재함.
- `brand_specificity_percentile` 등 일부 percentile이 여러 상권에서 완전히
  동일한 값으로 반복되는 이유(계산 방식) A에게 확인 필요. LLM-01 작업 자체에는
  영향 없음.
- 대표 브랜드의 설명을 B(XAI-01 담당)에게 전달하여, 모델 근거와 실제 서술이
  일치하는지 확인받는 절차가 워크플로우 문서상 필요함 (아직 미진행).
